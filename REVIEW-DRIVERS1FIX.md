# REVIEW — Clock 14 drivers1fix (spot-check of the fix round for drivers1 P1–P4 and the PIN cooldown)

This is a spot-check, not a full re-review. I did not modify either tree. All probes, tree copies and mutants are under `/tmp/d1fix/`:
- `old/` and `fix/` are my probes, bundled against each tree.
- `oldtree/` is drivers1 with the new test files dropped in.
- `fixtree/` is a copy of drivers1fix.
- `mut/<name>/` holds the mutants.

The probes reuse my drivers1 harness: localStorage is persisted to a JSON file and **each stage runs in a separate Node process**, so the module-load `bootFromStorage()` and `restoreUndo()` really run cold. `reloadVaultFromStorage()` is never used.

**Why SHIP.**
- P1, P2 and P3 each reproduce on drivers1 and are fixed on drivers1fix. I checked this with my own two-process probes, including the cross-driver cases.
- The new relaunch lane is a real two-process lane.
- The export and secret-scan pins catch every mutant I had in drivers1, plus a harder one.
- The cooldown works as specified.
- The engine is byte-identical, the storage keys are unchanged, and the diff touches only the fix.

Two of the new pins are weaker than the handoff claims (N1, N2). The behaviour they target is still correct and is covered elsewhere, so they don't block.

## Nits (non-blocking)

- **N1. DRR5 is not a fail-before pin.** It passes on drivers1. It registers Charlie from a cold, *never-locked* state, so the live `SIM_KEY` is still present and drivers1's unguarded stash happens to capture it correctly. The P3 bug needs lock-then-register, which DR7 pins (it fails on drivers1 and on the P3reg mutant). The handoff label "P2+P3 … catches" overstates it. Either make DRR5 lock first or relabel it.
- **N2. DRR6 doesn't catch the legacy leak coming back.** With the `completeLegacyDriverSetup` live-undo read re-added (mutant `P3leg`), Bob's snapshot **is** written into Lena's persisted profile; my debug run shows `lena undoRaw {"label":"Deleted On Duty…`. But the first render's `currentUndo()` retires the mismatched snapshot, and that calls `syncActiveUndoRaw(null)`. So by the time DRR6 asserts (after `sleep(40)`), Lena's profile is clean and the pin passes 6/6. To catch it, assert on Lena's profile *synchronously*, right after `completeLegacyDriverSetup` returns and before any render tick. The shipped code doesn't have the leak; this is only about regression protection.
- **N3. The anonymous bug-report pin tests `exportState(getState(), '')` directly, not `reportBug`.** Reverting `reportBug` to `exportState(s)` still passes `drivers` 11/11. The fix itself is in place (app.tsx:389). Consider a grep-style static check or exporting a payload builder.
- **N4. The cooldown is in memory, so a cold relaunch (swipe away, reopen) clears it.** That trade-off was part of my recommendation and I accept it: it turns 5 guesses per 30 s into 5 guesses per app relaunch, which is still real friction by hand. Worth a sentence in the handoff so nobody believes it survives a restart. `reloadVaultFromStorage()` also clears it, but nothing in `src/` calls that.
- **N5. A successful recovery reset clears the PIN counter too** (`clearAuthCooldown(driverId)`). That's fine: whoever passes recovery owns the account anyway.
- **N6. The handoff says "6 distinct salts" for 2 drivers, i.e. 2 PINs plus 4 answers.** That's correct. The salts are per secret, as I noted in drivers1.
- Carried over and still open from drivers1 (they were out of scope here): N2 Erase-sheet copy, N3 splash theme, N4 corrupt-vault re-migration, N7 `unlockSplashInBrowser` failing silently.
